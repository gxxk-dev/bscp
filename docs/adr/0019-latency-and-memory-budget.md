# 解析的延迟与内存预算：分段超时、逐页进度、页位图压缩存放

课前准备的等待时间要能被忍受，而且**看得见在等什么**。本页给的是工程判断而非不可逆
决定，但它的后果跨好几张票（进度 UI、超时降级、内存形态），所以写下来而不是留在票里。

## 预算

单份资料（首版上限 10 页，[ADR-0017](./0017-cap-pages-at-ten.md)）从点「解析」到碎开出现：

| 段 | 预算 | 超时怎么办 |
|---|---|---|
| 上传 + 栅格化 | ≤ 8s | **整份失败**，画布保持原样 |
| 视觉层（版面检测 + 区域分割） | ≤ 15s | **整份失败，并指出第几页** |
| 分组（多模态 LLM） | ≤ 15s | **不分组，解析仍然成功** |
| 裁切区域小图 | ≤ 2s | **整份失败** |

**目标合计 ≤ 30s（p90），硬上限 90s。** 视觉层页间独立，并行度 ≥ 4。

## 三个由预算逼出来的决定

### 一、页位图以压缩 PNG 存放，按需解码

A4 在 300 DPI 下是 8.7M 像素，一页解码后约 26MB。10 页全解码着就是 **260MB**——
几个并发会话就把 [ADR-0014](./0014-session-holds-page-bitmaps-in-memory.md) 的会话
撑爆，而内存根本没有必要花在这里：**裁切只需要一次解码一页，解完就释放。**
存压缩字节，10 页约 20–40MB。

300 DPI 本身不动（[ADR-0008](./0008-image-only-rasterize-first.md) 的精度选择），
省内存靠**存放形态**而不是靠降精度。

### 二、上传体积上限 30MB

延迟预算的第一段就是上传，而**一份 10 页的 600dpi 扫描 PDF 可以有 100MB 以上**。
按校园网 10–50 Mbps 算，100MB 就是 16–80 秒——整份预算的一半花在传文件上。

所以闸门再加一条：资源 ≤ 30MB，超出拒收，话术与格式、页数一致（说清是哪一份、
多大、怎么办）。**体积上限与页数上限是同一个理由的两面**：两者都是为了首版
把单次准备的等待压进 30 秒。

### 三、必须逐页显示进度

最长的一段是 15 秒，整体 30 秒。这个量级上「解析中…」三个字是不够的——
操作者会以为卡死了，然后开始乱点。**进度要显示到页**：「正在切第 3/10 页」。

顺带：视觉层结果按 `(页位图内容哈希, 视觉层实现版本, 配置)` 在会话内缓存。
重跑时若三项都没变，直接命中缓存跳过最慢的一段——重跑因此是快的，
而这正是「不可撤销」（[ADR-0011](./0011-no-rollback-rasterize-once.md)）能被接受的
前提之一：**不可撤销的东西，如果重跑要等 90 秒，就没人敢用了。**

## Consequences

- **视觉层超时不降级为「部分页」。** 编排缺内容比不解析更糟——漏掉的页要到讲台上
  才发现。所以要么整份出来，要么明确失败并指出是哪一页出的问题。
- **分组超时不降级为「部分分组」。** 已经有明确的降级路径（不分组），不需要更细的粒度。
- **这些数字是首版起点，不是承诺。** 拿真试卷跑一遍之后要回来改：延迟预算的
  作用是让「等多久算正常」成为一个可讨论的数字，而不是每次现场凭感觉。
- 单张图片（无需栅格化）走最短路径，目标 ≤ 5s——那是零模型的那条路，
  也是最该先跑通的一条。
