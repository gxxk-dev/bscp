# 资源的身份是内容哈希，不是文件名

一份资源的 id = 它**上传内容的哈希**。同内容 = 同一份资源，不管文件名叫什么；
不同内容但同名 = 两份不同的资源。

角标上显示的是该资源**首次登记时**的文件名。把同一份内容再投一次，不新增区域，
回执说「这份已经在画布上」。

## 为什么

**因为文件名是最不可靠的身份。** 校内场景里同一份卷子会以好几个名字出现：
下载器重命名成「卷子(1).pdf」、老师拷成「月考卷最终版.pdf」、另一台电脑上叫
「高一物理 9 月.pdf」。用文件名当身份，同一份资料会被算成三份，重跑时不知道该清哪份。

**因为服务端本来就要读文件。** 判格式、算大小、渲染页位图都要读一遍，多一次 SHA-256
是毫秒级开销（10 页 PDF 几 MB）。用内容当身份几乎是免费的。

**因为它让「同一份资料再投一次」成为一个真实可用的动作。** 操作者误投了一份、
或者想把另一门课的同一份卷子并排放，两次投放会合并成一份——而按文件名算，
他会得到两份一模一样的东西摆在画布上，还得自己删一份。

## Consequences

- **区域的归属键是 `(资源哈希, 区域内 id)`**，不需要自增 id。原型里 `artifact` 兼任
  显示名与归属的做法到此为止（[ADR-0012](./0012-reparse-one-artifact.md) 已经标出这个问题）。
- **文件名降级为显示属性**，不再是身份。角标、分组提议、回执都读它，但它不参与任何相等判断。
- **「重新栅格化换 DPI」仍然不成立**（ADR-0011 已取消）。内容哈希在这里的作用是
  识别与去重，不是「以后还能拿它重新渲染」。
- 会话里同一哈希的页位图只存一份（[ADR-0014](./0014-session-holds-page-bitmaps-in-memory.md)），
  重复投放直接命中已有会话数据。
