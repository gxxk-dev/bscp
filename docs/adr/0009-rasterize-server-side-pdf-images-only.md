# 栅格化在服务端用 PyMuPDF，首版只支持图片与 PDF

**栅格化这一步跑在服务端的 Python 运行时里**（PyMuPDF），不在浏览器。首版接受的输入是
**图片 + PDF**，**不支持 DOCX**。

三条来自同一轮的决策，合起来是一个形态：

| 决策 | 内容 |
|---|---|
| 栅格化位置 | 服务端（PyMuPDF 渲染，可指定 DPI，可缓存） |
| DOCX | **首版不做**，推迟到有真实需求时 |
| 输入格式 | 图片（原样）+ PDF（服务端栅格化） |

## 为什么

**DOCX 是唯一需要「引入一个渲染引擎」的格式，而它带来的复杂度与它的收益不成比例。**

ADR-0008 把管线塌缩成一条的前提是「除了 PDF 之外不需要渲染引擎」——但这条对 DOCX
不成立。DOCX 的逐字坐标不存在，**必须有人渲染它**，而 [ADR-0007](./0007-dual-input-single-ai-pipeline.md)
已经把三条渲染路线的代价都调研清楚了，**没有一条便宜**：

- 服务端 LibreOffice：镜像 **0.5–1.0 GB**，且官方 bug tracker 上「headless 转 PDF 卡死 /
  内存耗尽 / 非确定性换行」**全部仍是 open**，缺中文字体必然被替换（官方帮助页承认）
- 浏览器 LibreOffice WASM：传输 **≈53 MB**、运行时 **1 GB 级内存**，还需 COOP/COEP 隔离
- 纯 JS 库：无坐标，只能预览

**而 DOCX 不是核心故障。** 本项目的核心故障是「排版不适合投屏」，而校内最常见的输入是
**扫描件与拍照的试卷**——这也正是 [ADR-0002](./0002-text-layer-first.md) 当初把扫描件
称为「常见输入」的原因。DOCX 是可以推迟的，不是可以砍的核心。

**栅格化放服务端，是因为它必须与缓存和原始资源在一起。** [ADR-0008](./0008-image-only-rasterize-first.md)
说栅格化是可缓存的中间产物、且原始资源必须保留以便换 DPI 重新栅格化——这两件事都要求
有一个「知道资源在哪、能按哈希查缓存」的地方，那只能是服务端。

## Considered Options

- **首版就支持 DOCX（服务端 LibreOffice）**：吞下 0.5–1 GB 镜像与全部 open bug，
  换来一个可以推迟的格式支持。
- **首版就支持 DOCX（浏览器 WASM）**：不给服务端负载，但在大屏一体机上 53 MB 的加载
  与 1 GB 内存是现场体验问题。
- **栅格化放浏览器（PDF.js）**：本可省掉服务端的 PDF 渲染负载，但与「按哈希缓存」
  和「保留原件换 DPI」两件事冲突——浏览器没有稳定的缓存位置（[ADR-0005](./0005-parse-on-demand-overwrite-everything.md)
  明令不做客户端持久化）。

## Consequences

- **服务端不需要 LibreOffice。** ADR-0007 里那个 0.5–1 GB 的镜像彻底不用装，
  连带它全部未修复的 headless bug 也一并不必面对。服务端的 Python 依赖只剩
  PyMuPDF + PaddleOCR（[ADR-0006](./0006-self-hosted-vision-layer.md)）。
- **DOCX 需要一个明确的失败出路**：操作者投进 DOCX 时，系统必须给出可理解的拒绝
  （或提示「另存为 PDF 再投」），而不是静默失败。这是首版必须实现的负面路径。
- **「纯 SPA」的形态被确定否定**：栅格化在服务端、视觉层在服务端（ADR-0006），
  因此前端是 SPA，但**后端必须存在**。这坐实了 BYOK / 纯前端提案不可行——
  不是因为 key 的问题，而是因为**这两件事物理上需要服务端算力**。
- **图片输入是零成本的**：图片不需要栅格化，直接进解析。因此「图片」这条路径
  是整条管线最短的一条，也是最该先跑通的一条。
