# 页位图存在服务端进程内存：会话、不落盘、TTL 回收

一次「课前准备」= **一个服务端会话**。会话持有每一份资源的**页位图**；
前端持有**区域小图与编排**。页位图不落盘，会话按 TTL 回收。

- 上传时：服务端算内容哈希、渲染页位图，**随即丢弃原始字节**（不保留原件，ADR-0011）
- 解析完成时：把这一份资源所有区域的小图**一次性**返给前端
- 重跑时：前端请求该资源的句柄，服务端用**会话里的页位图**重跑——不需要原件
- 刷新页面：前端的编排与区域小图全没，会话随即无人认领，TTL 到期回收

## 为什么

**因为一页 A4 在 300 DPI 下是 8.7M 像素。** 页位图放前端，一份 10 页的资料就是
几十 MB 压在课堂那台一体机的浏览器里，而重跑还要把它再传回服务端一遍。放服务端，
重跑就是纯服务端操作，不跨网络。

**因为裁切在服务端做更稳。** 浏览器在 Windows 10 一体机上裁几 MB 的 canvas 未必流畅，
而 PyMuPDF 裁一个框是一行。区域小图在解析完成时一次性生成，前端只拿成品。

**因为不落盘就没有一整类问题。** 落盘就要回答「什么时候删、谁删、这份资料还在不在、
谁有权限读它」。不落盘，这些问题一个都不存在（ADR-0011 同一精神）。

**因为刷新即空，与「用完就关」一致。** ADR-0005 已经定了编排只在内存、不做客户端
持久化。刷新之后前端没有任何状态可以恢复，会话也就没有存在的理由。

## Consequences

- **服务端第一次有状态。** 需要三样东西：会话 id、TTL、以及「会话没了」时的明确错误
  （不是 404，更不是白屏——操作者要能知道是自己刷新了、还是等太久了）。
- **TTL 定为 30 分钟无活动**，从**最后一次用到会话的请求**起算；**解析中的会话
  不因 TTL 被回收**（一次 10 页的资料解析可能就要几分钟，回收一个正在解析的会话
  是最坏的时机）。取值待真实使用校准，但机制不再待定。
- **投屏期间不续期。** 投屏是纯前端行为（见下面那条），那时页位图已经用不上，
  让它按自己的 TTL 回收，而不是因为老师正在讲课就一直占着内存。
- **会话里不能有 API key，也不能有原始文件字节。** key 只在进程环境变量里。
- **投屏不需要会话。** 区域小图已经在前端，投屏是纯前端行为。会话只在解析与重跑时有用。
- **一次解析只有一次往返。** 上传换页位图与区域，页位图不出服务端。
- **会话里的页位图是管线内的当前状态，不是历史。** 它不违反 ADR-0011：那份被取消的是
  「为了换 DPI 而保留原件」，而这里连原件都不留。
- 首版单份资料的页数上限见 [ADR-0017](./0017-cap-pages-at-ten.md)，它同时让会话内存可控。
