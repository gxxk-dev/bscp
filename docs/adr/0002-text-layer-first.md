# 文字层优先：解析先读文档自带的文字，OCR 只用于无文字层的资源

> 本 ADR 已被 [ADR-0008](./0008-image-only-rasterize-first.md) 推翻——资源一律先栅格化，
> 不再读取文档自带的文字层。保留原文以备追溯（其中关于 `sort=True` 与多栏阅读顺序的
> 调研结论仍然成立，只是不再有文字层可读）。

PDF 与 Office 文档自带文字层，PyMuPDF 与 python-docx 能给出每个文字段的精确坐标、字体与字号。
这是**读出真字**，不存在识别误差，也不需要任何模型。因此解析按「这份资源有没有文字层」分流：
有文字层就直接抽取；无文字层（图片、扫描件 PDF）才交给决策模型做版面检测与 OCR。

扫描件是常见输入，所以 OCR 不是边缘情况，而是与抽取并列的一条主分支，要按一等公民的工程质量来做。

## Considered Options

- **一律走 OCR**：管线统一，但对自带文字层的资源是拿真字去换猜测，白白引入识别误差。
- **一律走抽取**：主路径零误差，但扫描件直接不可用——而扫描件恰恰很常见。

## Consequences

- 两条分支的产出必须归一到同一种「区域」结构，下游不区分来源。
- 需要能判定一份 PDF 是否含文字层，并把这一事实作为资源的固有属性持久化。
- 扫描件的 OCR 精度要求远低于「矢量化重排」路线：因为区域默认保留原始位图
  （见 [ADR-0001](./0001-keep-original-bitmap-regions.md)），OCR 只用于语义分组，
  认错个别字不致命——这让我们可以放心用便宜的模型。
- **文字层给的是字与坐标，不给阅读顺序。** 官方 FAQ 明确 `sort=True` 只按 block 的
  坐标全局排序，**两栏排版必然交错**，并直言「列边界要自己识别，没有万能解」。
  因此即使资源带文字层，**多栏的阅读顺序仍然需要版面模型**（官方生态的解法是
  `pymupdf-layout`，ONNX 权重，CPU 可跑）。
  这一条修正了「主路径不需要模型」的说法：**文字层省掉的是 OCR，省不掉版面**。
