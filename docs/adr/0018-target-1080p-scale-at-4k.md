# 目标分辨率 1920×1080；4K 下整套 UI 等比放大一档

目标屏是 **1920×1080** 的触控一体机。也会有人以 **4K（3840×2160）** 打开——
浏览器以 100% 缩放打开 4K 时，CSS 像素的**物理**尺寸减半：36px 的按钮只剩约 3mm，
48px 的触控命中区约 4mm，远低于 8mm 的建议值。控件在 4K 上不做处理是不能用的。

**办法：视口 ≥2560px 宽时，把根字号从 16px 提到 20px。** Tailwind 的尺寸全部由
rem 驱动（`--spacing: 0.25rem`），改根字号等于**整套 UI 等比放大**——间距、圆角、
字号一起变，不需要给任何组件写 4K 的特例类。20px 封顶：再大就该让浏览器或系统
去缩放，而不是我们把控件做成巨物。

## 为什么

**因为这是一块大屏触控屏，不是响应式网页。** 常规响应式网站的答案是「在窄屏上换布局」，
这里的答案是「在更密的像素上把同样的信息放到同样大的物理面积」——这两件事是反的。
用 rem 驱动 + 一处根字号，是唯一能让「同样的代码」在两种屏幕上物理尺寸一致的做法。

**因为逐组件写 4K 特例必然漏。** 只要有一个组件漏了，那个组件就是 4K 上唯一小的那个，
而它旁边的按钮都变大了——比全体不变还难看。

## Consequences

- **1080p 下不额外放大。** 36px 按钮配 48px 命中区在 1080p 上约 5–7mm，低于 8mm
  建议但可用。把 1080p 的按钮再放大到 48px 会让工具条变得笨重，而工具条必须能
  一眼扫完（[ADR-0011](./0011-no-rollback-rasterize-once.md) 那条工具条不变量）。
- **`fitView` 的 padding 改成按 rem 走**（现在硬编码 96 / 60px）。它决定画布四周
  留白与内容占比，屏幕变大而留白不变的话，画布在 4K 上会显得过满。
- **原型的 32 屏断言是按 1440×900 的桌面视口调的**，在 1920×1080 上要重跑一遍。
  冒烟脚本需要一个 1920×1080 的配置，与现有的 1440×900 并列——不是替换。
- 4K 档位**只改根字号一处**。任何「4K 下这个组件要特别处理」的需求都应视为
  「根字号档位选错了」。
