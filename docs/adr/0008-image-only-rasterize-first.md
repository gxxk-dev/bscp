# 一切资源先栅格化，区域永远是位图，矢量化降级为显式动作

输入只接受图片；PDF 与 DOCX 进来后**先整页栅格化成位图**，然后在位图上做区域裁切，
操作者拍板后区域上画布。**不存在自动矢量化管线**——所有区域默认永远是位图。

这条决定推翻了 [ADR-0002](./0002-text-layer-first.md)（文字层优先）与
[ADR-0007](./0007-dual-input-single-ai-pipeline.md)（OOXML 直解）：两者的前提都是
「从文档里读出真字」，而这里不再读字——**文档被当作图片看待**。

## 为什么

**收益是管线塌缩成一条。** 输入只有一种形态（位图），所以：

- 不存在「有文字层 / 无文字层」的分流，也不存在「PDF 路径 / DOCX 路径」的分流
- 不需要 PDF 文字层抽取、不需要 OOXML 解析、不需要 LibreOffice（省掉 ADR-0007 里
  那个 0.5–1 GB 镜像与其全部未修复的 headless bug）
- 决策模型的输入恒定是位图，后端可替换性变好（ADR-0006 的多后端因此更简单）

**代价是「字太小」这个原始故障失去了原有的解法**，见下。

## 代价与补偿

ADR-0001 保留矢量化的唯一理由是「字太小」——裁切位图放大即糊。砍掉自动矢量化后，
这个洞由两件事一起填：

1. **裁切可以切得更碎。** 解法从「重排文字」变成「切碎到放大够用」：一整个表格
   切成逐行、一道大题切成题干与选项，每块占的屏幕面积就更大，不需要拉伸像素。
2. **矢量化保留为显式动作**（见 [ADR-0001](./0001-bitmap-regions-vectorize-on-demand.md)
   的路线丙）。操作者可以对某一块单独发起矢量化，作为手工补丁——**不是管线的
   一部分，而是一个工具**。

补偿 1 是本 ADR 的实质内容：**它把「字太小」从渲染问题转成了切分粒度问题**，
而切分粒度恰好是本项目本来就要操作者拍板的东西。

## Considered Options

- **维持文字层优先**（ADR-0002）：主路径零误差，但引入两条输入路径与一套 OOXML 解析，
  且 DOCX 的非文字内容（插图、公式、手写）仍要另想办法——复杂度不低。
- **统一栅格化 + 保留自动矢量化**：即 ADR-0001 的原始形态。管线里多一条「判断哪些区域
  该矢量化」的自动分支，而这条判断恰恰最容易出错（矢量化失败时输出不可用的结果）。

## Consequences

- **栅格化是最上游的一步，它的分辨率是整条管线的精度天花板。** 因此
  **原始资源必须保留**：重新栅格化是换 DPI 的唯一手段，只留页图等于把最高精度
  锁死在第一次导入的那一刻。
- **栅格化是可缓存的中间产物**，按资源内容哈希缓存，复用 ADR-0006 已有的缓存机制。
  但缓存**不排除**保留原件——缓存是为了不重算，保留原件是为了能换精度。
- **「解析」这个词的含义收窄了**：它现在只指「在位图上切分区域」，不再包含任何
  文字抽取。术语已随之修订（见 `CONTEXT.md`）。
- **DOCX 的支持成本取决于谁来做栅格化**：浏览器侧需要 LibreOffice WASM
  （ADR-0007 已调研：约 53 MB 传输、1 GB 内存），服务端侧需要 LibreOffice 镜像。
  若两者都不接受，则 DOCX 需推迟到首版之后。
- **区域不可按内容定位，而这在本场景下无关紧要。** 位图里的字读不到，所以
  「打一个词跳到那个区域」做不到。但本工具的使用形态是「摆好 → 投出去 → 用完就关」，
  摆好即终点，不存在事后找回内容的需求（见 [ADR-0003](./0003-one-infinite-canvas.md)）。
  矢量化过的区域顺带可搜，这算白捡，不构成设计目标。
